# 术语表：让中文提问命中英文代码

## 解决什么问题

策划用中文问（「成就怎么算」「掉率配在哪」），但代码是英文（`Achievement`、`loot_chance`）。
直接拿中文去搜代码，往往只命中注释、甚至零命中。**术语表**把中文业务词映射到代码里真实
出现的英文符号，agent 据此把中文问题转成代码检索词。

它是**派生提示，不是答案**——只负责「该搜哪个英文词」，结论仍以实读代码为准。

## 怎么工作

分两段，对应上图左右两半。

**构建期（index 主机，离线）**——不在用户请求路径上，跟 git 刷新同节拍：
1. 扫本地代码副本：首次全量，之后按 `git diff` 只扫变更文件（增量）。
2. 本地 `claude` (cc) 读代码，产出「中文词 ↔ 英文符号」对照（JSONL）。cc 被锁定：禁写/执行/
   联网/子代理、不加载仓内 `.claude`——它只能读，不能被仓库里的内容操纵。
3. **grounding 校验**（确定性把关）：一个中文别名只有真实出现在源文件里才保留，否则丢弃——
   挡掉 cc 自己「翻译/臆造」出来的词。文档来源的词置信度降一档（见下「代码为准」）。
4. 写到 `/data/glossary/<项目>/<仓>.jsonl`，按项目、按仓隔离。

**查询期（会话 microVM）**——两个只读工具：
- `glossary_index`：会话开始时取一份轻量对照（高置信概念）。
- `glossary_lookup`：按**中文词**或概念 id 查完整符号集（含低置信的）。
- 拿到英文符号后，照常走 `search_files` / `symbol_search` / `read_file` 实读代码取证。

## 三条硬规则

- **代码为唯一依据**：扫描不限文件类型（代码 + 文档/README/设计案都扫，中文常在文档里），
  但**文档与代码冲突时以代码为准**——文档来源的条目置信度降一档，同概念下代码恒高于文档，
  文档词因此落到按需 `glossary_lookup` 层、不进显眼的 index。
- **不臆造**：grounding 校验保证中文别名都是源文件里真有的，cc 翻译出来的一律丢。
- **不破只读边界**：构建期引擎是「不跑引擎」MVP 约束的明确例外（离线、无会话、无用户输入），
  受 cc 锁定 + 产物只读服务 + 代码不出机器三重约束。详见 `invariants.md` §6 与 `AGENTS.md`「构建期引擎」。

## 实测效果与边界

在中文注释规范的大型项目（ET 框架，约 1.4 万候选文件）上实测：
- **配对率 ~98%**：抽出的概念几乎都「中文别名 + 英文符号」成对，可桥接。
- **桥接是数量级增益**：中文「成就」直搜代码 23 个文件 → 经术语表给出 `Achievement` 后命中
  many more 个文件；「分类」18 → 1525。中文只能搜到注释，桥接后定位到符号的全部实现代码。

**价值边界（诚实）**：
- 中文与符号相邻（注释、配置表表头——中文游戏项目的代码风格）时价值最高。
- 纯英文代码、无中文：术语表为空，但**无害**——`glossary_index` 返回空，agent 自动跳过，
  不影响现有问答。
- 覆盖率与构建文件上限 `MAX_BUILD_FILES` 正相关（`GLOSSARY_MAX_FILES` env / `--max-files`
  可配，0 = 不限）。大项目首次全量是一次性开销（约 1.4 万文件 ≈ a measured amount / 2 小时，cc 自主探索是
  主因），之后靠增量低成本维持。**默认 400 控成本，按需调高换覆盖。**

## 相关代码

- 数据层 `index-service/glossary.py`（concept 模型、聚合、来源分类/降级）
- 构建 `index-service/glossary_build.py`（cc 锁定调用、分批、grounding）、
  `glossary_gen.py`（CLI：全量 vs 增量、文件上限、原子写）、`glossary_refresh.sh`（刷新挂载）

- 接入 `http_bridge.py`（注册工具）、`agent-container/prompts/system.md`（引导首步查术语表）
