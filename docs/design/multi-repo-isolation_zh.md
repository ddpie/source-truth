# 多项目 / 多仓库的索引与隔离设计

> 设计权威依据：回答「一个机器人对应多个代码仓时，怎么索引、怎么路由、怎么保证不同项目之间不互相看到
> 代码」。这是 **post-MVP 能力**（MVP 仅单仓、仅主分支，见 [`requirements_zh.md`](requirements_zh.md)）。
> 本文只描述最终设计与安全不变量，不含实施步骤（步骤在 `.claude/plans/`）。架构总览见
> [`architecture-overview_zh.md`](architecture-overview_zh.md)。

## 1. 需求

客户是游戏研发团队。他们眼里的「一个项目」往往横跨多个代码仓——客户端、服务端、依赖库、若干微服务、
工具链。映射关系是：

```
飞书机器人 (bot) ──1:1──→ 游戏项目 (project) ──1:N──→ 代码仓 { 客户端, 服务端, 工具, ... }
```

由此引出两条核心诉求：

- **项目内联合检索**：一次问答常常跨同项目多个仓（前端调后端 API、微服务互调），必须能在项目的全部仓里
  联合查找。
- **项目间硬隔离**：机器人 A 绝不能看到机器人 B（另一个项目）的代码。

当前实现是**单仓假设**——一个 `graph.db`、一个 workspace、一把写锁。多仓不是「加个 for 循环」，它会冲击
下面的隔离与单写者不变量，必须按本文的设计落地。

## 2. 核心抉择：每仓独立建图，不合并

底层一律 **每个仓 = 一张独立 `graph.db` + 独立 workspace + 独立写锁 + 独立时效戳**，明确**不**把多个仓
塞进同一张图。理由：

1. **避免跨仓符号污染**：多仓重名符号会串、路径不再唯一、产生假的跨仓调用边。
2. **刷新粒度独立**：独占写入锁是「每图一把」，合并图意味着任一仓更新都要锁住并重建整张图；各仓更新频率
   天差地别，合并会互相拖累。
3. **合并并不带来跨仓能力**：前端→后端是 HTTP/RPC 的跨进程跨语言调用，静态调用图本就连不起这种边。
   **「跨仓」靠扇出查询 + 文本检索合并，不靠合并图。**

项目内的多仓能力是：给定 `repo` 入参就精确查某仓；不给就在项目的仓集合内**扇出查询、按相关度合并结果**，
每条结果按 `repo` 打标签。

## 3. 拓扑：项目间用进程边界硬隔离

每个项目一个常驻 bridge 进程（`http_bridge`），各自只挂载本项目的 N 个仓的图与本地副本。**项目间隔离靠
进程边界 + endpoint 注入**：每个项目的 agent 拿到的 `CODEGRAPH_MCP_URL` 指向只服务本项目的 bridge——
连上的进程里**根本不存在**别项目的图，模型够不到。项目内的多仓仍在同一个 bridge 里扇出。这正好匹配 §1 的
1:N 模型：**项目内共享、项目间隔离**。

规模假设：少量项目（≤ 约 10），同一台主机多进程、多端口部署即可，不必每项目一台实例。一次问答的流转：

```
飞书 @机器人
   │  gateway 按 bot → project → endpoint 路由（唯一可信源，见 §6）
   ▼
agent microVM（注入该项目专属 bridge 的 endpoint）
   │  给 repo → 精确查某仓；不给 → 在本项目仓集合内扇出，结果按 repo 合并
   ▼
该项目的 bridge 进程（只挂本项目 N 个仓的图 + 本地副本）
```

agent 看到的路径形如 `<repo>/<仓库相对路径>`（如 `backend-svc/Assets/Foo.cs`），既消歧又诚实，不引入虚假
mount 前缀。

## 4. 安全不变量

本节是设计的核心约束，落地时不可妥协。

### 4.1 隔离由服务端强制，不靠模型自觉

**「机器人只能看本项目代码」这条隔离，绝不能依赖 LLM 自觉填对 `repo` 参数。** 若把 `repo` 当成模型可填的
普通字段，那么一次 prompt 注入或 MCP 冷启动竞速泄漏，就能让 agent 把 `repo` 填成别项目的仓名而越权。

因此作用域钉死在 **endpoint + 服务端校验**，运行期模型无法覆盖：

- **白名单默认拒绝**：bridge 的「本作用域仓集合」以其启动参数（`--workspace` 集合）为唯一权威；`repo` 入参
  必须是该集合的成员，否则服务端**直接拒绝（403/404）**，不路由过去。默认值=空集=拒绝一切，绝不宽松放行。
- **realpath 二次防护**：`repo` 解析后必须再过一次 realpath 防穿越，且沙箱根**必须是解析后的具体仓目录
  `/data/repo/<resolved_repo>`，不得是项目根**——否则 `repo=repoA&path=../repoB/secret` 这类跨仓穿越会被
  放行。回归测试必须覆盖此用例。

这与现有「只读」边界是同一套哲学：mutating 工具根本不向模型注册 MCP 描述符，越界仓名同样由服务端拒绝。

### 4.2 单写者 per-graph + 崩溃隔离

每仓**独立 `graph.db` + 独立 flock 写锁 + 独立 `HOME`**（codegraph 把 `graph.db` 和 memory 都放
`$HOME/.codegraph`，多图共用一个 HOME 会互相覆盖）。由此「单写者」约束对每个仓自然成立，且**刷新/重启
单仓不影响其他仓**。

> 崩溃隔离有一个已知的硬前提：orphan reaper 用 `pgrep ... --workspace <ws>` 锚定时必须**末尾精确匹配**
> （如 `code-5x` 与 `code-5x-svc` 会前缀误匹配），否则一个仓重启会误杀另一个健康仓的 server，直接违反
> 「刷新单仓不影响其他仓」。这是多仓放量前必须先验的不变量。

### 4.3 只读边界不破

bridge 只注册只读工具（定位 + 读文件）。多仓新增的 `repo` 路由、术语表读取工具等一律保持只读，纳入服务端
闭合 allowlist。

### 4.4 路径诚实

工具返回 `<repo>/<仓库相对路径>`，不引入虚假 mount 前缀，沿用现有「返回仓库相对路径」的设计。

### 4.5 同主机多项目的补充边界

进程边界挡的是**经 MCP 工具的逻辑越权**，挡不住**主机级威胁**：任一 bridge 被 RCE，同 OS 用户即可直接
`open()` 读别项目源码。故同主机多项目至少要：(a) 每项目用独立 OS 用户跑其 bridge，`/data/<repo>` 设
`0700`，且首先让 bridge 不再以 root 跑；(b) index 服务用独立低权用户。**跨信任域 / 跨客户的项目不可同主机**，
需走实例 + 网络层隔离（单独 index-service 实例 + 安全组只允许对应会话访问）。

> 注意：`0700`/per-uid 只在「跨项目」生效。拓扑里**同项目的多个仓共进程、共 uid**，彼此无文件系统隔离。
> 故项目内隔离的唯一边界 = §4.1 服务端 allowlist + 进程不被 RCE。若某仓含只该被部分 agent 看到的敏感内容，
> 必须把它拆成独立进程（牺牲扇出），即「项目内若有不可互信的仓，也按跨信任域处理」。

## 5. 运维友好（一等设计目标）

多仓最大的运维风险是「仓越多，加仓/刷仓/排障越痛」。设计上把运维负担钉成硬约束：

**运维只在一处声明「哪个项目有哪些仓、各从哪来」(manifest)，其余全部由 deploy/bootstrap 据 manifest 自动
收敛**——建图、起服务、分端口、限内存、隔离、刷新、健康面。具体：

- **单一声明式可信源**：项目→仓→来源只在一处声明，不在多个脚本/env 里重复维护仓清单。
- **加/减仓 = 改一行 + 一条命令**：禁止运维手写 systemd 单元、手挑端口、手算磁盘。bootstrap 据 manifest
  自动为每仓实例化 build/serve 单元（systemd template）、自动分端口、按累计需求校验磁盘。
- **故障可归因到具体仓**：日志、单元名、健康探针都带 `<repo>` 维度，不允许「整个 index-service 不正常」
  这种说不清的状态。
- **幂等可回滚**：ETag 未变即 no-op，中途失败重跑不产生半成品；manifest 走 git review，改错能 revert。
- **安全默认零额外负担**：§4.5 的 per-project OS 用户 / `0700` / per-repo cgroup 由 bootstrap 据 manifest
  自动生成，是默认产物而非手工清单。生成它们属「特权操作生成特权配置」，repo 名进入 `useradd`/路径/单元名
  前必须过 `^[a-z0-9-]+$` 白名单，生成后要有机器可验证的事后断言（核对 uid、目录权限）。

## 6. 配置与路由

要管理的状态很少：一张映射表 + 两个动作（改映射、刷新某仓索引）。

```
bot → project → { repo 集合, endpoint }
repo → 来源（git URL / 分支 / S3 tar / 本地目录）
```

起步形态是**配置文件即权威依据**：工程团队改配置走 git review + 局部刷新，无新攻击面。需求升级时可演进到
「飞书内管理指令」（管理员 @机器人 触发刷新，复用现有通道，性价比最高的中间档）；只有当客户非技术人员要
大规模自助管理时，才上独立的 Web 管理后台——但那是一个**有独立安全面的新组件**（它改映射表 = 改谁能看
什么，必须连带鉴权 + 审计 + 变更流程一起设计），需独立立项，不能顺手加。

## 7. 实现现状：路由层已落地，多仓建图与硬隔离待实现

多项目能力分阶段落地，**安全闸门后置**——§4.1 的服务端越界拒绝就位前，多仓能力不得对多项目环境放量。

**阶段 1（已落地，gateway 路由层）**：`bot-gateway/src/project-routing.ts` 实现了 project→repos/endpoint 的
解析与校验，可独立于 index-service 多仓单独工作。

- 配置在 `.local/projects.json`（部署相关、gitignored），`config/projects.example.json` 是提交的 schema 模板；
  路径由 `PROJECTS_CONFIG_PATH` env 指定。
- 一个 gateway 服务哪个项目由 `PROJECT_ID` env 绑定；若只声明了唯一项目则零配置缺省命中它。
- **fail-closed / fail-loud 已实现**：配置缺字段/重复/格式错 → 启动即报错（不在请求期静默误路由）；未知或
  歧义的 `PROJECT_ID` → 拒绝派生路由（返回 null、记录日志，绝不回退到任意项目）；配置文件缺失则降级为
  「无 projectId 服务」（软失败，区别于「存在但非法」）。
- `projectId` 已作为低基数维度打到所有 metric；`repos` 已注入 invoke payload 转发给 agent。
- **注意**：路由对象里虽已解析出 `endpoint`，但 endpoint 真正用于驱动 agent 的 MCP URL 仍属后置——当前
  live agent 仍从运行期 env 读 `CODEGRAPH_MCP_URL`，per-project endpoint 路由随阶段 2+ 的多运行时工作落地。

**阶段 2 / 3（未落地）**：index-service 侧的多图（每仓独立 graph.db / HOME / flock / 端口、项目内扇出）与
服务端硬隔离（§4.1 的越界仓名拒绝 + realpath 二次防护）尚未实现。**这才是真正的多仓建图 + 跨项目硬隔离，
仍是设计待实现**——路由层选对了项目，但「服务端拒绝越界仓名」这道安全闸门还没建。阶段 3 就位前，多仓不放量。

## 8. 定时刷新（最终形态）

策划问答对代码新鲜度只需分钟级。最终形态用**定时拉**起步——无需在客户仓库侧配任何东西、不暴露接收端点
（零新增安全面）；webhook / inotify 增量索引仅预留接口、后置。

定时器周期触发「重新拉取来源 → 变了才重建该仓的图」，本质是**自动周期触发单仓刷新**，复用同一套机制
（per-repo flock、单写者、reaper 末尾锚定、per-repo cgroup），不另起炉灶。必守不变量：

1. **不重入**：上次重建未结束，定时器绝不再踢一次（并发写 `graph.db` → 0 节点损坏）。注意现有 flock 只锁
   graph.db 写、不含 `git pull` 改副本这一步，故不重入须靠**调度层串行**或**实例侧 per-repo flock 把整个
   `pull + rebuild` 一起包住**，文档须指明用哪层，不能含糊。
2. **副本原子切换**：拉取/重解包**绝不能原地 `rm -rf + 重写**——bridge 的读文件工具直接 `open()` 实时磁盘，
   原地改会与正在读的请求竞态（半个文件 / ENOENT / 新旧混读）。必须解包到 `<subdir>.new` 再 `rename` 切目录。
3. **变了才重建**：拉取后比对 commit / ETag，无变化就跳过，不空转重建。
4. **失败要响**：拉取/重建失败必须进监控告警——否则索引会静默停在旧版本，答案基于过期代码却显得很自信，
   对「代码为唯一依据」是隐性致命。

## 9. 项目术语表：中文提问命中英文代码的桥

策划用中文术语（「体力」「战力」「掉率」），代码里是英文字段名（`stamina`/`combatPower`/`dropRate`）。
没有映射，「代码为唯一依据」会断在第一步——agent 拿中文词定位不到英文符号。术语表就是这座桥，且带「业务
解释」后还是一份面向非技术读者的小型领域知识库。

### 9.1 存放：独立于代码副本，不进客户代码仓

**硬约束：不放客户代码仓、不干扰已有项目。** 术语表是 index-service 的独立数据资产，与代码副本物理并列：

```
/data/
├── repo/<subdir>/        ← 代码副本（只读，术语表不碰）
└── glossary/<project>/   ← 术语表（独立目录，与 repo 平行）
```

由 deploy/refresh 从独立来源（S3 / 团队自管小仓 / 本地文件）拉取，复用现有多来源 fetch；§8 刷新代码时顺带刷
术语表，同样适用「`.new` + rename 原子切换」（它刷新时也被独立工具实时 `open()`）。

### 9.2 读取隔离（不可省）

术语表物理上**在所有现有沙箱根之外**（现有文件工具沙箱根是 `/data/repo/<subdir>`，glossary 是其兄弟目录，
不在 §4.1 的 `--workspace` 集合里）。所以「隔离继承多仓边界」**不会自动成立**，必须显式规定：

- **新增独立只读读取工具**（不能复用现有 `read_file`，glossary 在其沙箱根外会被 realpath 直接拒）；
- 工具沙箱根**钉死在解析后的 `/data/glossary/<resolved_project>/`，绝不是 `/data/glossary/` 顶层**——否则
  `project=A&path=../B/...` 跨项目读别人术语表，正是 §4.1 的穿越翻版；
- 过同一套 realpath 二次防护 + `project` 名 `^[a-z0-9-]+$` 白名单 + 回归测试覆盖 `../B` 穿越；
- 纳入服务端只读 allowlist，不破坏只读边界。

### 9.3 结构与建法

CSV（纯文本、好 diff/review）：

```
中文名 | 英文名 | 代码符号/字段名 | 解释(业务含义) | 所属系统 | 别名
体力  | stamina     | maxStamina        | 玩家行动消耗资源，清零后无法行动，随时间恢复 | 背包/体力 | 精力,行动力
战力  | combatPower | CombatPower.calc() | 综合战斗强度评分，由属性+装备派生，非存储值   | 战斗     | 战斗力,BP
```

「代码符号/字段名」列是中文→代码的锚点（也是 §9.4 校验对象）；「解释」列契合「面向非技术读者」基线。
半自动建：英文侧/字段名用 `symbol_search` 抽代码符号、用 `search_files` 扫配置表表头（策划真正对位的字段
常只在 CSV/Excel 表头、不是代码符号）；中文名 + 解释人工补（解释是机器给不了、最有价值的一列）；高频问到
而表里没有的词逐步补入。

### 9.4 防过期：脱离代码仓后，自动校验是命门

术语表离开代码仓 = 脱离 PR review，比放仓内更易与代码漂移。校验从「建议」升为「必须」：

1. **符号存在性校验是降级信号，不是硬告警门**：CodeGraph 把空结果当作合法的「无匹配」，不区分「真不存在」
   与「召回不到」（动态语言、宏、配置驱动字段、GBK 仓召回不全是常态）。故「查不到」**不能逐条直接刷告警**
   （会持续误报 → 运维脱敏 → 形同虚设），而应：查不到只降 confidence、由 agent 用时标注「未在索引确认」；
   配置表列头用 `search_files` 全文兜底；告警阈值设成「某仓过期条目**占比突增**」而非逐条。
2. **术语表内容是不可信输入**：「解释」列会直接进 agent 回答，而来源脱离代码 PR review、可信度低于代码仓
   本身，是一条低门槛 prompt-injection 通道。故解释列进 agent 上下文前做**与用户提问同级的注入隔离**（核心
   是把不可信文本放进带分隔符的数据块、不与系统指令混排）；「代码符号」列喂校验前过字符白名单；明确**术语表
   信任等级 ≤ 它服务的代码仓**。
3. **agent 用时标注来源 + 过期降级**：基于术语表的翻译/解释要可追溯（与「供研发复核」证据面板一致）；命中
   低 confidence / 未确认条目则降级（提示转研发，不盲信）。

> 注意 `read_table` 有截断上限（每表 500 数据行 / 单元格 200 字符）：术语表超 500 行会被静默截断 → 中文词
> 命中不到被截条目 → 漏映射且无告警。对策是按系统/项目拆多张 CSV（每张 < 500 行）或提高该 cap，落地前必须
> 评估术语规模 vs 此上限。
