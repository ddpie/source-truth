# 多项目 / 多仓库的索引与隔离设计

> 设计权威依据：回答「一个机器人对应多个代码仓库时，怎么索引、怎么把问题路由到对的项目、怎么保证不同项目
> 之间互相看不到代码」。这是 MVP 之后的能力（MVP 只支持单仓、只读主分支，见
> [`requirements_zh.md`](requirements_zh.md)）。本文只讲最终设计与必须守住的安全底线，不写落地步骤
> （步骤在 `.claude/plans/`）。系统总览见 [`architecture-overview_zh.md`](architecture-overview_zh.md)。

## 1. 需求

客户是游戏研发团队。他们眼里的「一个项目」往往横跨多个代码仓库——客户端、服务端、依赖库、若干微服务、
工具链。对应关系是：

```
飞书机器人 ──1:1──→ 游戏项目 ──1:N──→ 代码仓库 { 客户端, 服务端, 工具, … }
```

由此引出两条核心诉求：

- **项目内联合检索**：一次问答常常要跨同一项目的多个仓库（前端调后端接口、微服务互调），必须能在该项目的
  全部仓库里一起查。
- **项目间彻底隔离**：机器人 A 绝对不能看到机器人 B（另一个项目）的代码。

现在的实现是按**单仓**写死的——一份代码图、一个工作目录、一把写锁。多仓不是「加个循环」那么简单，它会动到
下面的隔离与「同一份图同一时刻只许一个进程写」这两条底线，必须按本文设计来做。

## 2. 核心抉择：每个仓库各建一张图，不合并

底层一律是 **一个仓库 = 一张独立的代码图（`graph.db`）+ 独立工作目录 + 独立写锁 + 独立的新鲜度标记**，
明确**不**把多个仓库塞进同一张图。原因：

1. **避免跨仓库的符号串味**：多个仓库里同名的符号会混淆、路径不再唯一、还会生出根本不存在的跨仓库调用关系。
2. **刷新粒度互不拖累**：写锁是「一张图一把」。合并成一张图后，任何一个仓库更新都得锁住、重建整张图；而各
   仓库更新频率天差地别，合并只会互相拖累。
3. **合并也换不来跨仓库能力**：前端调后端是跨进程、跨语言的网络调用，静态代码图本来就连不起这种关系。
   **「跨仓库」靠的是分头查询再按相关度合并，不靠合并图。**

项目内的多仓库能力是这样：调用时指定了仓库就只查那一个；不指定就在该项目的所有仓库里**分头查询、按相关度
合并结果**，每条结果标明来自哪个仓库。

## 3. 部署形态：项目之间用进程边界来隔离

每个项目跑一个常驻的**索引服务进程**（即 `http_bridge`），它只加载本项目那 N 个仓库的图和本地代码副本。
**项目之间的隔离靠进程边界 + 服务地址下发**：每个项目的 agent 拿到的 `CODEGRAPH_MCP_URL` 只指向服务本项目的
那个进程——它连上去的进程里**根本就没有**别项目的图，模型够都够不着。项目内的多个仓库则仍在同一个进程里
分头查询。这正好对上 §1 的「一对多」结构：**项目内共享、项目间隔离**。

规模上的假设：项目不多（大约 10 个以内），同一台机器上多进程、多端口就够了，不必每个项目单开一台机器。
一次问答的流转：

```
飞书 @机器人
   │  网关按「机器人 → 项目 → 服务地址」路由（这张映射表是唯一权威，见 §6）
   ▼
agent 会话（注入了本项目专属服务进程的地址）
   │  指定仓库 → 只查那个仓库；不指定 → 在本项目所有仓库里分头查，结果按仓库合并
   ▼
本项目的索引服务进程（只加载本项目 N 个仓库的图 + 本地副本）
```

agent 看到的路径形如 `<仓库名>/<仓库内相对路径>`（如 `backend-svc/Assets/Foo.cs`），既消歧义、又如实，
不编造虚假的挂载前缀。

## 4. 安全底线

本节是设计的硬约束，落地时一条都不能让步。

### 4.1 隔离由服务端强制，不指望模型自觉

**「机器人只能看本项目的代码」这条隔离，绝不能寄望于大模型自己老老实实填对仓库名。** 一旦把仓库名当成模型
可以随便填的普通参数，那么一次提示词注入、或一次冷启动时的工具竞态泄漏，就能让 agent 把仓库名填成别项目的
仓库而越权。

所以可见范围钉死在 **服务地址 + 服务端校验**上，运行期模型改不动：

- **白名单，默认拒绝**：每个服务进程「能看哪些仓库」以它的启动参数（`--workspace` 列表）为唯一准绳；调用里
  指定的仓库必须在这个列表里，否则服务端**直接拒绝（403/404）**，不会替它转发。默认是空列表，也就是什么都
  拒，绝不放宽。
- **再用 realpath 防穿越**：仓库名解析成路径后，必须再用 `realpath` 校验一次，且校验的根目录**必须钉在解析
  出的那个具体仓库目录 `/data/repo/<仓库>` 上，不能是项目根**——否则 `仓库=A&路径=../B/secret` 这类跨仓库
  穿越就会被放过去。回归测试必须覆盖这种用例。

这和现有的「只读」边界是同一套思路：会改数据的工具压根不向模型登记，越界的仓库名同样由服务端挡掉。

### 4.2 每张图独占写入 + 崩溃互不牵连

**为什么这是铁律**：同一份 `graph.db` 被两个进程同时写，图会被**悄无声息地冲成 0 个节点**——查询返回空、
却不报错。这是「答得出话、却什么都查不到」最隐蔽的根因，单仓时代已经实测踩过。多仓把这个风险按仓库数翻倍，
所以「独占写入」必须**逐仓**成立。

每个仓库都有**独立的 `graph.db` + 独立写锁（flock）+ 独立的 `HOME` 目录**（codegraph 把图和记忆都放在
`$HOME/.codegraph` 下，多张图共用一个 HOME 会互相覆盖）。这样「同一份图同一时刻只有一个进程写」对每个仓库
自然成立，而且**刷新或重启某一个仓库，不会动到其他仓库**。

两台索引机器短暂并存是安全的（各自持有本地独立的 `graph.db`，没有共享的写入方），换机器时的「先起新、
再停旧」就建立在这一点上。

> 崩溃互不牵连有一个已知前提：清理僵尸进程时用 `pgrep … --workspace <目录>` 匹配，**结尾必须精确**
> （否则 `code-5x` 会误匹配到 `code-5x-svc`），不然重启一个仓库会顺手杀掉另一个健康仓库的进程，直接破坏
> 「刷新单个仓库不影响其他仓库」。这是多仓放量前必须先验证的一条。
>
> 配套规则：图是空的时候必须**报错、而不是返回空结果**——服务进程一旦发现 codegraph 报「0 个节点」就标记
> 自己不健康、拒绝服务，绝不让 agent 拿着一张坏图回答「查不到」（那违背「代码是唯一依据」）。但真实的
> 「符号确实不存在」查询本来就返回空，不能误判成坏图：判据是「0 节点」告警，不是「结果为空」。

### 4.3 只读边界不破

服务进程只登记只读工具（定位 + 读文件）。多仓新增的「按仓库路由」、术语表读取等工具一律保持只读，纳入
服务端那份封闭的白名单。

### 4.4 路径如实

工具返回的路径是 `<仓库名>/<仓库内相对路径>`，不编造虚假挂载前缀，延续现有「返回仓库内相对路径」的做法。

### 4.5 同机多项目还要补一层

进程边界挡得住**经由工具的逻辑越权**，挡不住**机器层面的威胁**：任何一个服务进程被攻破（远程代码执行），
同一个系统用户就能直接 `open()` 读别项目的源码。所以同机跑多项目，至少要：(a) 每个项目用各自独立的系统
用户跑它的服务进程，`/data/<仓库>` 设成 `0700`，并且首先别再用 root 跑；(b) 索引服务用独立的低权限用户。
**互不信任 / 不同客户的项目不能放同一台机器**，得靠机器 + 网络层隔离（各自独立的索引机器 + 安全组只放行
对应会话）。

> 注意：`0700` 和「按用户隔离」只在**项目之间**起作用。同一个项目的多个仓库是共进程、共用户的，彼此没有
> 文件系统隔离。所以项目内部的隔离边界只有一条：§4.1 的服务端白名单 + 进程不被攻破。如果某个仓库里有只该
> 给部分 agent 看的敏感内容，就必须把它拆成独立进程（牺牲掉分头查询），也就是「项目内部若有互不信任的
> 仓库，也当作跨信任域来处理」。

## 5. 运维省心（一等设计目标）

多仓最大的运维风险是「仓库越多，加仓、刷仓、排障越痛苦」。设计上把运维负担当成硬指标来约束：

**运维只在一个地方声明「哪个项目有哪些仓库、各自从哪来」（一份清单），其余全部由部署脚本照着清单自动
铺开**——建图、起服务、分端口、限内存、做隔离、刷新、健康视图。具体：

- **唯一声明处**：项目、仓库、来源只在清单里写一次，不在多个脚本或环境变量里重复维护仓库列表。
- **加 / 减一个仓库 = 改一行 + 跑一条命令**：不准运维手写 systemd 单元、手挑端口、手算磁盘。部署脚本照着
  清单自动给每个仓库生成构建 / 服务单元（用 systemd 模板）、自动分端口、按总量校验磁盘。
- **故障能定位到具体仓库**：日志、单元名、健康探针都带上「哪个仓库」，不允许出现「整个索引服务都不正常」
  这种说不清的状态。
- **可重复、可回退**：来源指纹（S3 的 ETag）没变就跳过不重建，中途失败重跑不会留下半成品；清单走 git 评审，
  改错能回退。
- **安全是默认产物，不增负担**：§4.5 的「按项目分用户 / `0700` / 按仓库限内存」都由部署脚本照清单自动生成，
  是默认就有、而非手工维护的清单。这属于「用特权操作去生成特权配置」，所以仓库名在进入建用户、拼路径、拼
  单元名之前必须先过 `^[a-z0-9-]+$` 白名单，生成之后还要有机器能自动核对的事后检查（核对用户、目录权限）。

> 一个易踩的坑：清单要用**一个完整的 JSON 变量**整体传给机器，别拆成一堆零散的环境变量。清单里带着每个
> 仓库的来源和 S3 ETag，而分段上传的 ETag 形如 `da58…-3`、拼多段时还夹着 `|`。这种值写进环境变量文件、再
> 被 shell `source` 读，裸值里的 `|` 会被当成管道执行，开了 `set -e` 时整个初始化脚本会在第一行就崩。单仓
> 时代已经两次被 ETag 里的特殊字符炸过 shell。规则：环境变量文件里每个值都加单引号；清单整体用一个 JSON
> 变量承载。

## 6. 配置与路由

要管的状态很少：一张映射表 + 两个动作（改映射、刷新某个仓库的索引）。

```
机器人 → 项目 → { 仓库集合, 服务地址 }
仓库  → 来源（git 地址 / 分支 / S3 包 / 本地目录）
```

起步形态是**配置文件即权威**：工程团队改配置走 git 评审 + 局部刷新，不引入新的攻击面。需求升级了可以演进到
「飞书内管理指令」（管理员 @机器人 触发刷新，复用现有通道，性价比最高的中间档）；只有当客户的非技术人员
要大规模自助管理时，才上独立的 Web 管理后台——但那是一个**自带独立安全面的新组件**（改这张映射表 = 改
「谁能看什么」，必须连同鉴权、审计、变更流程一起设计），得单独立项，不能顺手就加。

## 7. 实现现状：路由层已落地，多仓建图与硬隔离还没做

多项目能力分阶段落地，**安全闸门压在后面**——§4.1 的服务端越界拒绝没就位之前，多仓能力不得对多项目环境
放量。

**第一阶段（已落地，网关路由层）**：`bot-gateway/src/project-routing.ts` 实现了「项目 → 仓库集合 / 服务
地址」的解析与校验，可以独立于索引服务的多仓改造单独上线。

- 配置放在 `.local/projects.json`（与部署绑定、不进 git），`config/projects.example.json` 是进 git 的样例
  模板；具体路径由 `PROJECTS_CONFIG_PATH` 环境变量指定。
- 一个网关服务哪个项目，由 `PROJECT_ID` 环境变量绑定；如果只声明了唯一一个项目，则零配置默认命中它。
- **出错就拒、配错就崩，都已实现**：配置缺字段 / 重复 / 格式错 → 启动直接报错（不会在请求期悄悄路由错）；
  `PROJECT_ID` 未知或有歧义 → 拒绝派生路由（返回空、记日志，绝不回退到随便哪个项目）；配置文件不存在则
  降级为「不带项目标识照常服务」（这是软失败，与「文件存在但内容非法」区别对待）。
- 项目标识（`projectId`）已作为低基数维度打到所有监控指标上；仓库集合（`repos`）已塞进调用负载、转发给
  agent。
- **一点说明**：路由结果里虽然已经解析出了服务地址，但「用这个地址真正驱动 agent 连哪个索引服务」仍属后续
  ——当前线上 agent 还是从自己的运行期环境变量读 `CODEGRAPH_MCP_URL`，按项目切换服务地址要随第二阶段的多
  实例改造一起落地。

**第二、三阶段（未落地）**：索引服务侧的多图（每仓独立的 `graph.db` / HOME / 写锁 / 端口，以及项目内分头
查询）和服务端硬隔离（§4.1 的越界仓库名拒绝 + realpath 防穿越）都还没做。**这才是真正的多仓建图 + 跨项目
硬隔离，仍是待实现的设计**——路由层只是把问题分到了对的项目，但「服务端拒绝越界仓库名」这道安全闸门还没
建起来。这道闸门到位之前，多仓不放量。

## 8. 定时刷新（最终形态）

策划问答对代码新鲜度只要求到分钟级。最终形态用**定时拉取**起步——不需要在客户仓库那边配任何东西、也不
对外暴露接收端点（零新增攻击面）；webhook / 文件监听式的增量索引只预留接口、暂不做。

定时器周期性地「重新拉取来源 → 有变化才重建那个仓库的图」，本质上就是**自动周期性地刷新单个仓库**，复用
同一套机制（每仓写锁、独占写入、僵尸进程精确匹配、按仓库限内存），不另起炉灶。必须守住的几条：

1. **不重入**：上一次重建还没结束，定时器绝不能再踢一次（两个进程同时写 `graph.db` → 图被冲成 0 节点）。
   注意现有写锁只锁住「写图」这一步、不含「拉代码改本地副本」那一步，所以「不重入」要么靠**调度层串行**
   （上一次没返回就不发下一次），要么靠**机器侧的每仓写锁把「拉取 + 重建」整段包住**——文档必须写明用哪
   一层，不能含糊。
2. **副本原子切换**：拉取 / 重新解包**绝不能原地 `rm -rf` 再写**——服务进程的读文件工具是直接 `open()` 实时
   磁盘的，原地改会和正在读的请求撞车（读到半个文件 / 文件没了 / 新旧混读）。必须先解包到 `<目录>.new`、
   再用 `rename` 整体切换。
3. **有变化才重建**：拉取后比对 commit / ETag，没变化就跳过，不空转重建。
4. **失败必须吵**：拉取 / 重建失败必须进监控告警——否则索引会悄悄停在旧版本，答案基于过期代码却显得很
   自信，对「代码是唯一依据」是隐性致命伤。

## 9. 项目术语表：让中文提问命中英文代码

策划用中文术语（「体力」「战力」「掉率」），代码里却是英文字段名（`stamina` / `combatPower` / `dropRate`）。
没有这层对照，「代码是唯一依据」第一步就断了——agent 拿着中文词定位不到英文符号。术语表就是这座桥，带上
「业务解释」之后，它还是一份面向非技术读者的小型领域词典。

### 9.1 放哪：独立于代码副本，不进客户代码仓

**硬约束：不放进客户代码仓、不干扰已有项目。** 术语表是索引服务的一份独立数据，和代码副本物理并列：

```
/data/
├── repo/<仓库>/          ← 代码副本（只读，术语表不碰它）
└── glossary/<项目>/      ← 术语表（独立目录，与 repo 平级）
```

由部署 / 刷新从独立来源（S3 / 团队自管的小仓库 / 本地文件）拉取，复用现有的多来源拉取能力；§8 刷新代码时
顺带刷术语表，同样适用「`.new` + rename 原子切换」（它刷新时也正被读取工具实时 `open()`）。

### 9.2 读取隔离（不能省）

术语表在物理上**位于所有现有沙箱根之外**（现有文件工具的沙箱根是 `/data/repo/<仓库>`，术语表是它的兄弟
目录，不在 §4.1 的 `--workspace` 列表里）。所以「隔离自动继承多仓边界」这件事**不会自动成立**，必须显式
规定：

- **新增一个独立的只读读取工具**（不能复用现有的读文件工具，术语表在它的沙箱根之外会被 realpath 直接拒）；
- 这个工具的沙箱根**钉死在解析出的 `/data/glossary/<项目>/` 上，绝不能是 `/data/glossary/` 顶层**——否则
  `项目=A&路径=../B/…` 就能跨项目读别人的术语表，正是 §4.1 那种穿越的翻版；
- 过同一套 realpath 防穿越 + 项目名 `^[a-z0-9-]+$` 白名单 + 回归测试覆盖 `../B` 穿越；
- 纳入服务端只读白名单，不破坏只读边界。

### 9.3 结构与建法

用 CSV（纯文本、好 diff、好评审）：

```
中文名 | 英文名      | 代码符号/字段名    | 解释（业务含义）                               | 所属系统  | 别名
体力  | stamina     | maxStamina        | 玩家行动消耗的资源，清零后无法行动、随时间恢复   | 背包/体力 | 精力,行动力
战力  | combatPower | CombatPower.calc() | 综合战斗强度评分，由属性 + 装备派生，非存储值     | 战斗      | 战斗力,BP
```

「代码符号/字段名」列是中文到代码的锚点（也是 §9.4 的校验对象）；「解释」列正好对上「面向非技术读者」这条
基线。半自动地建：英文名 / 字段名用 `symbol_search` 抽代码符号、用 `search_files` 扫配置表表头（策划真正
对位的字段，常常只在 CSV/Excel 表头里、不是代码符号）；中文名和解释由人补（解释是机器给不了、最有价值的
一列）；高频被问到、但表里没有的词逐步补进去。

### 9.4 防过期：脱离代码仓后，自动校验是命门

术语表离开代码仓，就等于脱离了 PR 评审，比放在仓内更容易和代码渐渐对不上。所以校验从「建议」升级成「必须」：

1. **符号存在性校验是降级信号，不是硬告警**：codegraph 把空结果当成合法的「没匹配」，并不区分「真的不存在」
   和「召回不到」（动态语言、宏、配置驱动的字段、GBK 仓库召回不全都是常态）。所以「查不到」**不能逐条直接
   告警**（会持续误报 → 运维渐渐无视 → 形同虚设），而应该：查不到只降低置信度、由 agent 回答时标注「未在
   索引中确认」；配置表表头用 `search_files` 全文兜底；告警阈值设成「某个仓库过期条目**占比突然升高**」，
   而不是逐条。
2. **术语表内容属于不可信输入**：「解释」列会直接进 agent 的回答，而它的来源脱离了代码 PR 评审、可信度低于
   代码本身，是一条门槛很低的提示词注入通道。所以解释列进 agent 上下文前，要做**和处理用户提问同级的注入
   隔离**（核心是把不可信文本放进带分隔符的数据块里，绝不和系统指令混排）；「代码符号」列在拿去校验前先过
   字符白名单；并且明确**术语表的可信级别 ≤ 它服务的代码仓**。
3. **agent 回答时标注来源、过期就降级**：基于术语表的翻译 / 解释要能溯源（和「供研发复核」证据面板一致）；
   命中了低置信度 / 未确认的条目就降级处理（提示转研发，不盲信）。

> 注意配置表读取工具有截断上限（每张表 500 行数据 / 每格 200 字符）：术语表超过 500 行会被悄悄截断 → 中文
> 词命中不到被截掉的条目 → 漏映射且没有告警。对策是按系统 / 项目拆成多张 CSV（每张少于 500 行），或调高这个
> 上限；落地前必须先评估术语规模与这个上限的关系。
