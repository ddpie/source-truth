# 多项目 / 多仓库的索引与隔离设计

> 本文定义多项目 / 多仓的最终设计与安全底线；落地现状见 §7。系统总览见
> [`architecture-overview_zh.md`](architecture-overview_zh.md)。

## 1. 需求

游戏研发团队眼里的「一个项目」横跨多个仓库——客户端、服务端、依赖库、微服务、工具链：

```
飞书机器人 ──1:1──→ 游戏项目 ──1:N──→ 代码仓库 { 客户端, 服务端, 工具, … }
```

两条核心诉求：

- **项目内联合检索**：问答经常要跨同一项目的多个仓库（前端调后端、微服务互调），必须能一起查。
- **项目间彻底隔离**：机器人 A 绝对不能看到机器人 B 的代码。

现有实现按单仓固定——一份图、一个工作目录、一把写锁。多仓会动到隔离和「一图一写者」这两条底线，
必须按本文设计来做。

## 2. 核心抉择：一仓一图，不合并

**一个仓库 = 一张独立的 `graph.db` + 独立工作目录 + 独立写锁 + 独立新鲜度标记。** 不把多仓放进同一张图：

1. **符号不混淆**：多仓同名符号会混淆、路径不唯一、凭空产生跨仓调用关系。
2. **刷新互不拖累**：合并成一张图后任何仓库更新都得锁住全图重建；各仓更新频率差异很大，合并只会互相阻塞。
3. **合并也换不来跨仓能力**：前端调后端是跨进程网络调用，静态代码图本来就连不起来。
   **跨仓靠分头查询再按相关度合并结果，不靠合并图。**

调用时指定仓库则只查那一个；不指定则在该项目所有仓库里**分头查、按相关度合并**，每条结果标明来源仓库。

## 3. 部署形态：进程边界隔离项目

每个项目跑一个常驻 **索引服务进程**（`http_bridge`），只加载本项目的 N 个仓库。agent 拿到的
`CODEGRAPH_MCP_URL` 只指向本项目的进程——进程里**没有**别项目的图，模型无法访问。
项目内多仓仍在同一进程里分头查询。**项目内共享、项目间隔离。**

规模假设：项目约 10 个以内，同一台机器多进程多端口即可。流转路径：

```
飞书 @机器人
   │  网关按「机器人 → 项目 → 服务地址」路由（映射表见 §6）
   ▼
agent 会话（注入本项目服务地址）
   │  指定仓库 → 只查那个；不指定 → 全部分头查再合并
   ▼
本项目索引服务进程（只加载本项目的图 + 本地副本）
```

路径形如 `<仓库名>/<仓库内相对路径>`（如 `backend-svc/Assets/Foo.cs`），如实表示，不编造挂载前缀。

## 4. 安全底线

硬约束，一条不能让步。

### 4.1 隔离由服务端强制，不靠模型自觉

如果仓库名只是模型可填参数，一次提示词注入或冷启动工具竞态就能越权。可见范围固定在**服务地址 +
服务端校验**上，运行期模型无法修改：

- **白名单默认拒绝**：服务进程能看哪些仓库以启动参数 `--workspace` 为准；不在列表里直接 403/404。
  默认空列表。
- **realpath 防穿越**：仓库名解析成路径后必须 realpath 校验，根目录固定在 `/data/repo/<仓库>`
  而不是项目根——否则 `仓库=A&路径=../B/secret` 就会穿透。回归测试必须覆盖。

思路同现有只读边界：写操作不登记，越界仓库名由服务端拦截。

### 4.2 一图一写者 + 崩溃互不牵连

同一份 `graph.db` 被两个进程同时写，可能**静默写成 0 节点**（查询返回空却不报错），单仓时代遇到过。
多仓把风险按仓库数翻倍，独占写入必须**逐仓**成立。

每个仓库有独立的 `graph.db` + 独立写锁（flock）+ 独立 `HOME`（codegraph 在 `$HOME/.codegraph` 存图，
共用 HOME 会互相覆盖）。刷新或重启某仓库不影响其他仓库。

两台索引机器短暂并存是安全的（各自独立 `graph.db`，无共享写入方），换机器「先起新再停旧」建立在这一点上。

> 僵尸进程清理 `pgrep … --workspace <目录>` 匹配必须精确（否则 `code-5x` 会误杀 `code-5x-svc`）。
> 多仓扩大使用范围前必须验证。
>
> 图为空（0 节点）时必须报错并拒绝服务，不让 agent 拿坏图回答。判据是 0 节点，不是结果为空。

### 4.3 只读边界不破

服务进程只登记只读工具。多仓新增的路由和术语表读取工具一律只读，纳入白名单。

### 4.4 路径如实

返回 `<仓库名>/<仓库内相对路径>`，不编造挂载前缀。

### 4.5 同机多项目须补操作系统级隔离

进程边界能阻止逻辑越权，挡不住 RCE：服务进程被攻破后，同一系统用户可直接读别项目源码。同机多项目至少要：

- 每个项目用独立系统用户跑服务进程，`/data/<仓库>` 设 `0700`，不使用 root。
- **互不信任的项目不放同一台机器**，靠机器 + 安全组隔离。

> 同一项目的多仓是共进程共用户的，彼此无文件系统隔离。项目内若有互不信任的仓库，必须拆成独立进程
> （牺牲分头查询），当作跨信任域处理。

## 5. 降低运维负担（一等设计目标）

仓库越多，加仓 / 刷仓 / 排障越痛苦。设计原则：**运维只维护一份清单（哪个项目有哪些仓库、来源是什么），
其余全部由部署脚本按清单自动生成和部署。**

- **唯一声明处**：项目、仓库、来源只在清单里写一次。
- **加减仓库 = 改一行 + 执行一条命令**：脚本自动生成 systemd 单元、分端口、校验磁盘。
- **故障定位到具体仓库**：日志、单元名、健康探针都带仓库标识。
- **可重复可回退**：ETag 没变就跳过；中途失败重跑不留半成品；清单走 git 评审。
- **安全是默认产物**：分用户 / `0700` / 限内存由脚本自动生成。仓库名入路径前过 `^[a-z0-9-]+$` 白名单，
  生成后自动核对权限。

> 清单用**一个完整 JSON 变量**整体传给机器，别拆成零散环境变量。S3 分段上传的 ETag 含 `|`，裸写进 env
> 文件被 shell source 时 `|` 当管道执行，`set -e` 下第一行就会失败。单仓时代因此触发过两次脚本失败。规则：env
> 文件值加单引号；清单整体 JSON 承载。

## 6. 配置与路由

状态很少：一张映射表 + 两个动作（改映射、刷新索引）。

```
机器人 → 项目 → { 仓库集合, 服务地址 }
仓库  → 来源（git / S3 / 本地目录）
```

起步**配置文件即权威**：改配置走 git 评审 + 局部刷新，不增加攻击面。后续可演进到飞书管理指令（管理员
@机器人 触发刷新）。独立 Web 管理后台是自带安全面的新组件（改映射 = 改谁能看什么，需鉴权 + 审计 +
变更流程），得单独立项。

## 7. 实现现状

落地形态：**单机多项目，逻辑隔离（进程 + 端口 + 服务端 scope gate）**，机器人（独立飞书 App）1:1 项目、
项目 1:N 仓库，全部共用一台 index EC2。

- **配置真相源**：`.local/projects.json`（不进 git，模板 `config/projects.example.json`），每个项目一条：
  `port`（该项目 bridge 端口，全机唯一）、`feishuSecretId`、`repos`（每仓 `{subdir, git, ref?,
  refreshIntervalSec?}`，git-only）。网关启动时校验，配置错即启动失败。
- **网关路由**（`bot-gateway/src/project-routing.ts`）：网关服务哪个项目由 `PROJECT_ID` 绑定（唯一项目零配置
  自动命中），解析出该项目的仓库集合与 bridge 端口，`projectId` 写入监控指标。
- **索引侧多图**：每个仓库独立 `graph.db` / HOME / 写锁；每个项目一个 bridge 进程 `index-bridge-<projectId>`
  在独立端口只服务本项目仓库（`activate_project.sh`）。
- **每项目独立 runtime**：`source_truth_agent_<projectId>`，其 `CODEGRAPH_MCP_URL` 指向本项目 bridge 端口——
  agent 取证连接按项目隔离。

**安全说明**：当前是逻辑隔离（A 档，适用互相信任的项目同机）。§4.5 的操作系统级隔离（独立系统用户 / `0700`，
防 RCE 后横向读取）尚未做——互不信任的项目须分机器。服务端越界仓名拒绝 + realpath 防穿越（§4.1）为强化项。

## 8. 定时刷新

问答对新鲜度只要求分钟级。**落地形态**：每个仓库一个 systemd timer（`index-refresh-<subdir>.timer`，默认
300s，`projects.json` 可配）周期性 `git pull`；常驻 codegraph `--mcp` 进程的 file-watcher 在文件落盘后数秒内
增量重建内存图——无重启、无第二个写者。不对外暴露端点（零新增攻击面）；webhook / push 触发为预留项。

满足的约束：

1. **不重入**：刷新只 `git pull`（幂等），不另起 codegraph 进程；watcher 串行处理文件事件——天然不重入，不会
   并发写同一张图。
2. **接受 pull 瞬间中间态**：原地 `git pull`（不做 `.new`+rename）；watcher 是文件粒度增量，pull 半途的瞬间
   读到中间态会被下一个文件事件纠正。graph.db / HOME 在工作树内，由 `git_fetch.sh` 的围栏与 `git reset --hard` 隔离（见 §4.2 / 不变量5）。
3. **有变化才重建**：HEAD 未变即无文件事件，watcher 自然跳过。
4. **失败必须告警**：`git pull` 失败打 `GIT_FETCH_FAILED` 标记（可接监控），不让索引静默停在旧版本。

## 9. 项目术语表：让中文提问命中英文代码

策划说「体力」「战力」「掉率」，代码里是 `stamina` / `combatPower` / `dropRate`。没有这层对照，agent
用中文词定位不到英文符号。术语表提供这层映射，带上业务解释后也是一份面向非技术读者的小型领域词典。

### 9.1 存放位置

**不放进业务代码仓。** 术语表是索引服务的独立数据，与代码副本物理并列：

```
/data/
├── repo/<仓库>/          ← 代码副本（只读）
└── glossary/<项目>/      ← 术语表（独立目录）
```

从独立来源（S3 / 小仓库 / 本地文件）拉取，刷新时同样适用 `.new` + rename 原子切换。

### 9.2 读取隔离

术语表在现有沙箱根 `/data/repo/<仓库>` 之外，隔离**不会自动继承**，必须显式规定：

- 新增独立只读读取工具（不能复用现有读文件工具，会被 realpath 拒）。
- 沙箱根固定在 `/data/glossary/<项目>/`，不能是 `/data/glossary/` 顶层（防 `../B` 穿越）。
- 使用同一套 realpath + 项目名 `^[a-z0-9-]+$` 白名单 + 回归测试。
- 纳入只读白名单。

### 9.3 结构与建法

CSV（纯文本，便于 diff 和评审）：

```
中文名 | 英文名      | 代码符号/字段名    | 解释（业务含义）                            | 所属系统  | 别名
体力  | stamina     | maxStamina        | 玩家行动消耗的资源，清零后无法行动、随时间恢复 | 背包/体力 | 精力,行动力
战力  | combatPower | CombatPower.calc() | 综合战斗强度评分，由属性+装备派生，非存储值    | 战斗      | 战斗力,BP
```

「代码符号」列是中文到代码的锚点；「解释」列面向非技术读者。半自动建表：英文名 / 字段名用
`symbol_search` 抽符号、`search_files` 扫配置表表头；中文名和解释由人补；高频被问到但表里没有的词
逐步补入。

### 9.4 防过期

术语表脱离 PR 评审后更容易和代码对不上，校验从建议升为必须：

1. **符号校验是降级信号，不是硬告警**：codegraph 不区分「真不存在」和「召回不到」（动态语言、宏、GBK
   仓库都是常态），逐条告警会持续误报直到运维无视。做法：查不到只降低置信度，agent 标注「未在索引中确认」；
   告警阈值设为某仓库过期条目**占比突然升高**。
2. **术语表是不可信输入**：「解释」列脱离代码评审，容易成为注入通道。进 agent 上下文前做和用户提问同级的
   注入隔离（不可信文本放带分隔符的数据块，不和系统指令混排）；「代码符号」列先过字符白名单。术语表可信
   级别 ≤ 它服务的代码仓。
3. **标注来源、过期降级**：基于术语表的翻译要能溯源；低置信度条目降级处理（提示转研发，不直接采信）。

> 配置表读取工具有截断上限（每表 500 行 / 每格 200 字符）。术语表超限会被静默截断，导致漏映射。对策：按系统
> 拆成多张 CSV（每张 < 500 行），或调高上限。
