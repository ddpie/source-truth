# 游戏研发助手｜需求与方案评审（2026-06-16）

## 背景

客户侧的策划、QA、客户运营需要频繁了解代码逻辑与配置，现状依赖打断研发或查阅过时文档。已有同事在本地
经飞书查代码，但属非官方、无人维护，且各自部署存在账号成本、技术门槛、代码外泄隐患（前端约 15G，
下载慢）。诉求：在飞书内提供统一的代码问答助手。

## 核心结论

第一版 MVP 以**代码为唯一依据、仅查主分支**，技术栈为 **Claude Code + AgentCore Runtime（会话隔离）
+ 共享存储 + CodeGraph 类索引**，以「开箱即用、又快又好、交互体验」为验收基准。曹豹搭建 MVP 并做性能
对比，客户侧负责真实环境部署验收。

## 决策事项

| 维度 | 决策 | 依据 |
|-|-|-|
| 事实源 | 以代码为唯一依据 | 文档常滞后；配置与源数据基本在工程内 |
| 范围 | MVP 仅查主分支 | 诉求是了解已上线功能；多分支后置 |
| 运行环境 | AgentCore Runtime 会话隔离 | 每会话独立容器，秒级冷启、空闲约 15 分钟回收；Session Storage 约 14 天过期 |
| 存储 | 共享存储，默认 EFS（待实测） | 关注读延迟，先实测，瓶颈出现再换 EBS/SSD |
| 索引 | 项目级索引，程序自动生成 | 后端多仓，需先定位查哪个工程；工程内检索交给 Claude Code |
| 模型 | MVP 用 Claude Code | 先走 API 计费，后续评估订阅 |
| 机器人 | 每个游戏项目一个机器人 | 机器人内按会话隔离 |
| 共享记忆 | 不做（后置） | 易污染、返回过时答案 |
| 代码定位索引 | MVP 采用 CodeGraph 类索引（待 POC 验证） | 多仓定位关键，召回率/时延待验证；更深结构索引后置 |
| 审计护栏 | 第一版不做（后置） | 先以日志防滥用 |

## 核心体验要求（老白提出，决定产品上限）

| 要求 | 含义 |
|-|-|
| 开箱即用 | 免部署、免下载安装、免申请账号，移动端可用，显著降低门槛 |
| 又快又好 | 速度快于本地，且回答质量高 |
| 交互体验 | 卡片化、去刷屏进度、说人话、结构化，可附推荐问题；参考 GenSpark、腾讯 WorkBuddy |

## 关键讨论

**速度与项目级定位。** 未指定目录时全量扫描慢（演示 50 秒至 5 分钟），指定目录后明显加快；后端多 git
仓库时助手难自动判断该查哪个。MVP 采用 CodeGraph 类索引做代码定位，先定位到正确工程、再由 Claude
Code 在工程内检索；目标是叠加索引后速度快于本地，待 POC 验证。

**交互体验。** 避免命令刷屏；长任务需让用户感知仍在工作；输出结构化、便于阅读。

**规模并发。** 单项目 10 至 30 人，同时并发不超过 5，低频无规律。

**会话隔离。** 上下文挂在飞书对话、按需拉取消息记录；多用户不可共用 session，否则相互串扰。

### 客户环境（会上已澄清）

| 项 | 结论 |
|-|-|
| 引擎与语言 | 前端 Unity 风格 C#，约 15G；后端 Node.js，微服务架构，分散为多个 git 仓库（单仓体量小） |
| 版本管理 | 内网 GitLab，需反向拉取或打包至 AWS |
| 配置表 | 当前版本配置均在工程内；少量运行期可改项在数据库，后置 |
| 分支 | 每功能一分支，MVP 仅查主分支 |
| 模拟与写回 | MVP 仅只读问答，不跑引擎、不写回、不提交 |
| 设计文档 | MVP 不纳入，只关注代码；后续再考虑接入 |

## 待验证技术点与风险

### 待验证技术点

- CodeGraph 对前端 C# 与后端 Node.js 的索引召回率；
- push 到索引的端到端时延与首次全量索引耗时；
- CodeGraph stdio 到 HTTP 桥接的稳定性与并发；
- EFS 同卷并发挂载，及 NFS 上 inotify 增量的可靠性；
- EFS 读取性能（索引定位加点名读取 与 全仓兜底两条路径）；
- 飞书流式卡片频控、图表组件边界、动态组件回调路由。

### 风险

| 风险 | 判断 |
|-|-|
| 共享存储瓶颈 | 先实测，瓶颈出现再换 EBS/SSD |
| Session Storage 为 Preview | 商用前复核，备单机加网关方案 |
| 速度能否超越本地 | MVP 已含 CodeGraph 类索引，目标快于本地，需 POC 验证召回率与时延 |
| 合规与越权 | 不用共享账号；护栏与审计第一版后置 |
